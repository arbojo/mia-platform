# ADR-023: API & WebSocket Diagnostic Tooling

## Status

Accepted

## Date

2026-08-13

## Council

Aprobado por el Engineering Council (TASK-20260813-063009991, 7/7 agentes) con las deliberaciones P3 y P5 ratificadas el 2026-08-13.

---

## 1. Context

El Bridge Baileys usa WebSockets reales y existe una necesidad concreta de diagnosticar conexión, handshake, `ws-token`, flujo de sesión y comportamiento del bridge con independencia de la UI. Además, MIA debe disponer de una forma reproducible y versionable de probar sus APIs sin depender exclusivamente de la UI ni de la configuración local de un desarrollador.

Principio: **problema real → capacidad necesaria → herramienta mínima → contrato reproducible.** No adoptar múltiples clientes API redundantes (HTTPie/Postman/Insomnia quedan fuera).

## 2. Decision

- **wscat**: herramienta mínima de diagnóstico WebSocket externo del bridge. **P3 (ratificado)**: `wscat` como devDependency de la raíz (`^6.1.0`) + script de respaldo `scripts/ws-diagnose.mjs` (Node puro sobre `ws ^8.18.0`, sin shims/ejecutables) + `core.longpaths=true` documentado para Windows. Los respaldos redundantes eliminan el punto único de fallo: el diagnóstico nunca depende de la salud de `node_modules` ni de shims de plataforma.
- **Bruno**: herramienta primaria de pruebas API manuales/reproducibles, **condicionada** a que las colecciones sean versionables y pertenezcan al repositorio (`bruno/`), no a la config local de un desarrollador. **P5 (ratificado)**: blindaje de `bruno/` con (1) `.gitignore` estricto que ignora TODO el directorio `bruno/environments/` excepto `*.example.bru`/`*.template.bru`, (2) GitHub Push Protection habilitado en el repo, y (3) `scripts/secrets-check.mjs` integrado en el CI (validate.yml).
- No se adoptan otras herramientas WebSocket ni clientes API adicionales.

### P3 — wscat como devDependency (no instalación global nativa)

- Instalación global nativa por máquina queda descartada: es configuración tribal sin contrato ni versión fijada. `devDependency` en la raíz = versión fijada + lockfile + `npx wscat` idéntico en Linux/Windows.
- Evidencia de robustez: wscat `^6.1.0` depende de `{ ws, read, commander, https-proxy-agent }` — **JavaScript puro, sin addons nativos** (el "binding de red" vive en el propio Node). No hay compilación por plataforma ni ejecutables con permisos nativos.
- Riesgos reales de Windows mitigados: (a) límite `MAX_PATH` 260 → `npm config set core.longpaths true` + ruta de clon corta; (b) execution policy de PowerShell bloquea `.ps1`, no los shims `.cmd` de npm; (c) `node_modules` corrupto → respaldo `npm run ws-diagnose` (usa `ws` del bridge como fuente secundaria).
- `scripts/ws-diagnose.mjs` es el mismo diagnóstico sin wscat: `npm run ws-diagnose -- --url "wss://<bridge>/v1/ws?businessId=<id>&token=<signed>"`. Es la herramienta mínima de respaldo, no una herramienta adicional: reutiliza `ws` ya presente.

### P5 — blindaje de secretos en bruno/

Ningún error humano puede hacerse "imposible", pero sí **inofensivo**, en tres capas:

1. **Estructural**: los valores reales solo pueden vivir en un fichero de entorno local; el `.gitignore` ignora todo `bruno/environments/` salvo los ejemplos. El error típico (pegar el token real donde toca) queda **invisible para git**.
2. **Servidor**: Push Protection de GitHub bloquea el push si detecta un token conocido (claves Supabase, `sk-`, etc.). El repositorio es público → la protección está disponible. Es el backstop que sobrevive a cualquier error local.
3. **CI**: `npm run secrets-check` escanea `bruno/` y falla la pipeline (validate.yml) si aparece un patrón de secreto, ignorando placeholders `{{VAR}}` / `{{process.env.VAR}}` para no generar falsos positivos.

Se descarta git-crypt para `bruno/`: cifraría las colecciones y las haría ilegibles en el repo, destruyendo su propósito de lectura rápida (git-crypt sigue cubriendo `.env`).

## 3. Evidence

**WebSocket real confirmado** — `services/whatsapp-bridge/src/server.ts:150`:
`new WebSocketServer({ server, path: '/v1/ws' })` (dependencia `ws ^8.18.0` en `services/whatsapp-bridge/package.json`).

**Autenticación del WS** — `server.ts:152-160`: query params `businessId` + `token`; token = HMAC-SHA256 base64url del `WHATSAPP_BRIDGE_SECRET` sobre `businessId`; rechazo con `ws.close(4401, 'Unauthorized')`. El token se obtiene de `GET /api/channels/baileys/ws-token` → `{ token, wsUrl: "wss://<bridge>/v1/ws", businessId }` (`src/app/api/channels/baileys/ws-token/route.ts`).

**Uso wscat canónico**:
```
npx wscat -c "wss://<bridge>/v1/ws?businessId=<id>&token=<signed>"
```

**Respaldo sin wscat** (Node puro, `scripts/ws-diagnose.mjs`):
```
npm run ws-diagnose -- --url "wss://<bridge>/v1/ws?businessId=<id>&token=<signed>"
```

**Sintaxis de variables en Bruno** (verificado en docs oficiales): los entornos se referencian como `{{VAR}}` (fichero de entorno) y los secretos del SO como `{{process.env.VAR}}` (fichero `bruno/.env`). No se usa la notación `{{env.VAR}}`, que no resuelve en Bruno.

**Endpoints candidatos iniciales para Bruno** (81 rutas en `src/app/api`):
- `GET /api/system/health`
- `GET /api/channels/connections`
- `GET /api/channels/baileys/ws-token`
- `GET /api/channels/baileys/session`
- `POST /api/channels/baileys/followup`
- `POST /api/channels/baileys/reconnect`
- `POST /api/channels/baileys/webhook`
- `POST /api/channels/webhook/[channel]`

**Autenticación de la app**: las rutas usan cliente Supabase server con cookie de sesión (`supabase.auth.getUser()`); el token de WS valida además ownership del negocio.

## 4. Scope

- Añadir `wscat ^6.1.0` y `ws ^8.18.0` como devDependencies de la raíz + scripts `ws-diagnose` y `secrets-check`.
- Crear `scripts/ws-diagnose.mjs` (respaldo Node puro sobre `ws`, con fallback al `ws` del bridge).
- Crear `scripts/secrets-check.mjs` (scan de patrones sobre `bruno/`, ignora placeholders).
- Crear colección Bruno inicial (salud + canales) versionada en `bruno/` del repo, con 0 secretos.
- Plantilla de entorno Bruno (`bruno/environments/local.example.bru`) con placeholders `{{VAR}}`, sin secretos.
- `.gitignore` estricto para entornos locales Bruno.
- Integrar `npm run secrets-check` en el CI (validate.yml).
- Activar GitHub Push Protection en el repositorio (paso manual en Settings → Code security; ver Riesgos).
- Documentar diagnóstico wscat + respaldo + `core.longpaths` Windows en `docs/infrastructure/ws-diagnostics.md`.
- Formalizar en este ADR.

## 5. Non-goals

- No instalar Bruno como dependencia ni en el repo ni en CI (Bruno es una app de escritorio; las colecciones se versionan en `bruno/`).
- No HTTPie/Postman/Insomnia adicionales.
- No modificar producto ni bridge.
- No git-crypt para colecciones Bruno (haría ilegible la colección en el repo).

## 6. Files affected

`bruno/` (colecciones `.bru` + `bruno.json` + README), `bruno/environments/local.example.bru` (ejemplo versionado; el resto de entornos, gitignored), `scripts/ws-diagnose.mjs`, `scripts/secrets-check.mjs`, `package.json` (devDeps `wscat`/`ws` + scripts), `.gitignore` (entornos Bruno), `.github/workflows/validate.yml` (paso Secrets Check), `docs/infrastructure/ws-diagnostics.md`, `docs/adr/ADR-023.md`.

## 7. Risks

- Colección versionada con secretos → mitigado en 3 capas: `.gitignore` estricto (valores reales solo en entorno local ignorado), Push Protection de GitHub (bloquea el push), `npm run secrets-check` en CI (falla la pipeline). El repo es público: el coste de un fallo sería la exposición inmediata de credenciales de canales de clientes, por eso la capa de servidor es obligatoria.
- Endpoints auth-dependientes no testables sin sesión → la colección separa públicos (`/api/system/health`) de los que requieren cookie (`SESSION_COOKIE`) o webhook secret (`x-mia-webhook-secret`).
- Dependencia de una sola máquina → mitigada por repo-ownership desde el día 1 + respaldo `ws-diagnose` (Node puro) que no depende de shims ni de la salud de `node_modules`.
- Windows `MAX_PATH` (260) → `core.longpaths=true` + ruta de clon corta, documentado en `ws-diagnostics.md`.

## 8. Gates

- `npm run secrets-check` (integrado en validate.yml) sobre los `.bru` — 0 patrones de secreto.
- Revisión de que ningún `.bru` contenga valores reales (solo placeholders `{{VAR}}` / `{{process.env.VAR}}`).
- Lint/build intactos (solo se añaden archivos Bruno, scripts y docs).
- Push Protection habilitado en GitHub (manual, verificado en la sesión).

## 10. Acceptance criteria

- `bruno/` en el repo con colección ejecutable contra variables de entorno, 0 secretos (verificado por `secrets-check`).
- Comando wscat documentado y reproducible contra el bridge (staging), con respaldo `ws-diagnose` Node puro.
- ADR-023 aprobado por el Council (Status: Accepted).

## 11. Consequences

- Diagnóstico WebSocket del bridge sin depender de la UI, con redundancia (wscat + Node puro) que aguanta cambios de máquina imprevistos (Linux/Windows).
- Pruebas API reproducibles por cualquier miembro del equipo en cualquier máquina (Linux/Windows).
- Blindaje de `bruno/` en 3 capas: la infraestructura de diagnóstico no es una bomba de tiempo de credenciales.
- Materializa el principio de contrato reproducible para testing manual.
